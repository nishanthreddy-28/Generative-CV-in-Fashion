# Dashboard, profile contracts and remaining API gaps

Local implementation, 2026-11-09. No hosted changes or foundation flag enablement.

- GET /dashboard counts actual owned wardrobe garments, saved outfits, generated results, bookmarks and try-on jobs. Existing owner indexes support aggregate filters. Generated-result count includes history whose garments later became unavailable; this is labeled generated recommendations, not currently available looks. Frontend refreshes on focus and supports empty/error states.
- Profile/preferences PATCH sends only present fields into atomic row-locked merges; omitted fields survive, empty optional text explicitly clears, null/unknown values are rejected. Incomplete bootstrap names no longer block updating an unrelated profile field. Body-profile behavior and unresolved measurement/unit product decisions remain unchanged.
- Additive Auth provisioning trigger reads display name only, never editable roles; idempotent backfill repairs missing application records without reactivating disabled/deleting users. Supabase's real Auth schema contains raw_user_meta_data; minimal local fixtures model provisioning in a dedicated trigger test.
- DELETE /outfits/{id} removes the owning aggregate/items only. Frontend confirmation is restored. POST /outfits accepts the existing recommendationId variant, locks owned history, validates current sources through aggregate creation, copies outfit metadata/item associations without duplicating garments, and keeps detachable provenance. Unique owner/recommendation provenance and serialization return the existing outfit on repeat saves. Bookmark removal remains independent. UI offers Save as outfit beside Save recommendation.
- Password change now performs same-identity Supabase reauthentication and updateUser instead of a preview-only success message. Google sign-in uses Supabase OAuth PKCE, a fixed project authorization URL and oauth-callback code exchange. Native callback uses drapedrop://oauth-callback; web uses the same origin. Web access/refresh sessions remain memory-only; a dedicated sessionStorage adapter persists only the short-lived PKCE code verifier across the OAuth redirect. Provider credentials, real redirects and Android deep-link acceptance still require configuration/testing. See [Supabase OAuth](https://supabase.com/docs/reference/javascript/auth-signinwithoauth) and [PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow).

New migrations: 202611090004_dashboard.sql, 202611090005_profile_integration.sql, 202611090006_outfit_gaps.sql. All are additive/local and preserve existing data/security boundaries. Ordinary user calls use current JWT/RLS; no privileged fallback. Hosted bootstrap must be reviewed with the exact Auth trigger and backfill before approval.
