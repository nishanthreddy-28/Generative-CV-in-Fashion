## Ordered execution and evidence requirements

1. **Target/preflight:** record project reference, environment confirmation, server version, migration hash and existing object/role/config inventory. Inspect existing collisions and privileges before applying anything. Reuse the exact approved migration; if hosted permissions expose a defect, report it and make a separately reviewable corrective migration rather than silently changing the baseline or weakening grants.
2. **Apply/inspect:** apply `202611060001_foundation.sql` once via trusted migration authority. Run [read-only inspection](../../supabase/verification/inspect_foundation.sql) and save sanitized evidence. Confirm six tables, Auth FK ownership, standalone tombstone without Auth FK, enabled/forced RLS, exact execution-role attributes, direct and transitive role membership, editable-column grants, function ownership/search paths/EXECUTE, default grants and restrictive Storage policy. Inspect effective privileges, not only information_schema listings. No test-only Auth/Storage primitive SQL is permitted on Supabase.
3. **Exposure:** inspect actual Data API configuration and expose `api` for the existing wrappers; keep `app_private` unexposed. Preserve and review existing schemas/settings rather than overwriting blindly. Check actual HTTP schema selection with Content-Profile/Accept-Profile. Both private schema rejection and denied base writes matter. An HTTP error alone is not evidence of row isolation: positive permitted controls must also succeed.
4. **Real identities:** provision distinct A, B and catalog-admin test accounts in Auth. Inspect authoritative user records and actual signing/JWKS configuration. Use trusted bootstrap for each intended active account; do not infer email verification from arbitrary token claims. Obtain real sessions through Auth; do not manufacture JWTs or set request claims manually. Keep tokens/passwords only in private ephemeral test storage and redact them from output. Use a separate unbootstrapped account to verify fail-closed behavior.
5. **JWT/ownership:** for A and B, call account_access and require returned userId to equal the cryptographically verified subject; call/read/update their profile/preferences with distinct test markers. Interleave concurrent requests using one transport, then re-read each account and independently inspect scoped persistence to prove no cross-user writes/leaks. Repeat after token refresh, failure and cancellation. Confirm the same current JWT reaches normal calls and no service credential is attempted. Test both POST RPC and GET where supported, missing/invalid/expired tokens, foreign/extra owner arguments, direct base table and private-schema attempts, protected functions and metadata-role escalation. Do not add diagnostic endpoints.
6. **Lifecycle:** retain the same unexpired JWT. Disable A with the trusted operation and prove normal profile/settings reads and writes are denied through direct Data API; use an in-memory test application configuration if FastAPI verification is needed, without editing the deployed/default feature flag. Re-enable only the disabled test subject to verify recovery. Transition a separate active subject to deleting, verify denial and retained minimal tombstone, and prove reactivation/bootstrap cannot bypass it. Do not delete real accounts or describe begin-deletion as complete cleanup. Repeat inactive denial for a catalog-admin subject. Test an unbootstrapped identity and dependency failures.
7. **Storage HTTP:** use a dedicated **private verification bucket**, synthetic non-personal test image and uniquely prefixed test paths. Inspect real schema/ownership conventions first. Provision narrowly scoped temporary test authorization only for that bucket and current-subject paths; the existing restrictive lifecycle policy grants no positive access by itself. Record/remove only the exact temporary policies/bucket/fixtures created for this run. Positive active owner upload/download/list/replace/delete/signing controls must succeed; B access to A paths and anonymous private/public-route reads must fail. Reuse an unexpired JWT after disabling/deleting its owner and test authenticated download, listing, upload, replacement, deletion and new URL signing. Obtain a signed URL while active and separately measure its behavior after disable: any remaining validity is a capability limitation requiring an explicit decision, not an authorization pass. Never print signed URLs or upload personal images. An all-denied bucket is not successful authorization verification. Do not relax the restrictive gate to make tests pass.
8. **Trusted administrator boundary:** grant/revoke catalog_manage through the existing trusted operator, verify current_catalog_admin/account_access changes for the correct subject only, and reject ordinary direct membership/lifecycle changes and forged user_metadata roles. Confirm admin cannot read/write B's private profile/preferences and is denied when disabled/deleting. There is no catalog table yet: these checks verify membership authority, not nonexistent catalog CRUD.
9. **Review/cleanup:** record observed results with timestamps, exact assertion and sanitized request/status/evidence references, including failures. Clean only uniquely identified test fixtures using approved trusted cleanup; never reactivate deleting subjects or purge evidence under an invented retention policy. Remove temporary Storage policies so they cannot become production permissions. Verify the backend environment flag is still false. Hosted acceptance requires all mandatory checks and explicit disposition of capability/retention questions; a failed/not-run check must remain visible.
10. **Activation gate:** provide the completed evidence report for review. Never enable the feature flag while required checks are incomplete. This preparation does not enable it; the initial milestone boundary remains in force.
