# Drape & Drop mobile data audit

Audited 11 November 2026 IST against `main` at `92edaca` and the uncommitted mobile fixes described below. Scope covers the Expo Router routes, components, feature modules, hooks, API and Auth clients, theme, and domain types under `mobile/src`. Backend evidence comes from `backend/app`, `backend/registration`, and `supabase/migrations`.

The reviewed production route implementations source business records from FastAPI or Supabase Auth. The audit found a synthetic garment label and fallback states that could misrepresent server results. No seeded or hardcoded garment, outfit, recommendation, profile, measurement, catalog product, customer account, or dashboard statistic was found in the reviewed production route data paths. Hosted authenticated workflows and native Android restart remain separate acceptance checks.

## Screen-by-screen sources

Paths in this section refer to FastAPI unless prefixed by `/auth/v1` or `/auth/registration`. Application tables below live in `app_private`. The mobile client never queries those tables directly.

### Public and authentication screens

- **`/` — Landing.** Displays branding, navigation, and three bundled editorial JPEGs from `mobile/assets/editorial`. There is no product list, customer record, statistic, or business-data endpoint. The images are campaign assets.
- **`/login` — Sign in.** Email/password come from the form. Supabase Auth `POST /auth/v1/token?grant_type=password` authenticates against `auth.users` and `auth.identities`. FastAPI `GET /admin/catalog/access` returns the same subject UUID and trusted role decision from lifecycle, verification, and administrator controls. `GET /account/deletion` is used when normal access is denied and deletion progress may be available.
- **`/signup` — Create an account.** The form sends the entered email to coordinator `POST /auth/registration/start`. It uses `registration_challenges` and `registration_rate_windows`; the returned attempt binding is retained for verification. There are no bundled account credentials or identities.
- **`/verify-registration` — Dual verification.** Coordinator `POST /auth/registration/status`, `/link`, `/verify`, `/resend`, and `/finalize` (all under `/auth/registration`) source verification and resend status from the challenge and rate-window tables. Finalization writes the trusted receipt to `registration_receipts`, creates the verified Supabase Auth identity, and invokes the application provisioning path. Link proof and code proof must both succeed. Local Mailpit delivery was used only for the disposable local audit accounts.
- **`/auth-confirm` — Auth email callback.** Supabase Auth `POST /auth/v1/verify` verifies the supplied email-link token against Auth-managed state. This route does not create a coordinator receipt or substitute for dual verification.
- **`/forgot-password` — Recovery request.** Supabase Auth `POST /auth/v1/recover` receives the entered address. The generic acknowledgment intentionally does not reveal whether an account exists.
- **`/reset-password` — Recovery completion.** Supabase Auth `POST /auth/v1/verify` with recovery type and `PUT /auth/v1/user` using the recovery session update the Auth credential. The password is form input and does not become an application record.
- **`/oauth-callback` — OAuth.** Where enabled, the entry forms read `GET /auth/v1/settings` and start `GET /auth/v1/authorize` with the provider. The callback exchanges the bound PKCE code through `POST /auth/v1/token?grant_type=pkce` and then applies the same FastAPI account-access check. Provider identities live in Supabase Auth. Real Google or Apple sign-in was outside this run's runtime evidence.
- **`/privacy` and `+not-found`.** Static redirect and navigation/error views. No record reads. The root `_layout` enforces route boundaries and renders navigation.

### Customer screens

- **`/dashboard` — Home.** Recent outfit names and item references are from `GET /outfits?limit=4`, which reads `saved_outfits` and `outfit_items`. A first-piece thumbnail uses the referenced garment's authenticated image endpoint. The shortcut tiles and section text are static. The screen displays no aggregate statistics. Separate `GET /dashboard` computes real counts from `wardrobe_garments`, `saved_outfits`, `recommendation_results`, `saved_recommendations`, and `tryon_jobs`; verified by local API call.
- **`/profile` — Personal profile.** `GET /profile` and `PATCH /profile` read and update name, style notes, location, and bio in `user_profiles`. Blank controls represent absent fields or unsaved input. Local API write/read passed.
- **`/profile/body` — Measurements and fit.** `GET /profile/body` and `PATCH /profile/body` read and update height, chest, waist, hips, inseam, measurement units, preferred fit, body shape, skin tone, and undertone in `body_profiles`. An omitted measurement is left blank. No default measurement or inferred body attribute is displayed. Local API write/read passed.
- **`/preferences` — Account preferences.** `GET /settings` and `PATCH /settings` read and update units and email-notification preference in `user_preferences`. The separate light/dark appearance toggle is a client presentation setting.
- **`/settings` — Account.** The email comes from the Supabase session and the role comes from `GET /admin/catalog/access`, backed by `administrator_memberships` and account eligibility state. Password reauthentication and changes use `POST /auth/v1/token?grant_type=password` and `PUT /auth/v1/user`; sign-out uses `POST /auth/v1/logout`. The deletion action uses `DELETE /account` to write a deny-first lifecycle state and cleanup task. It shows acknowledgment after acceptance.
- **`/account-deletion` — Cleanup status.** `GET /account/deletion` reads `deletion_tasks` and account lifecycle status. The UI distinguishes a missing request from an accepted request with no accompanying message. Local status read and disposable database tests passed. An actual hosted deletion was outside scope.
- **`/wardrobe` — Owned garments.** `GET /wardrobe` supplies paginated names, categories, and metadata from `wardrobe_garments`. `GET /wardrobe/{garment_id}/image` obtains authenticated bytes via `wardrobe_images` and private bucket `wardrobe-images`. Category/sort filters are fixed API input options. Results and cursors are supplied by the API.
- **`/wardrobe/add` — New garment.** Multipart `POST /wardrobe` persists entered metadata and the selected file to `wardrobe_garments`, `wardrobe_images`, and the private bucket. The camera/file preview is unsaved user input. The form provides neither inferred attributes nor product-link extraction.
- **`/wardrobe/[id]` — View/edit/delete garment.** `GET /wardrobe/{garment_id}`, authenticated image GET, multipart `PATCH /wardrobe/{garment_id}`, and `DELETE /wardrobe/{garment_id}` use the same owner-scoped sources. Local API created two garments, renamed one, read real JPEG bytes, and rejected another user's reads, writes, deletes, and image fetches.
- **`/catalog` — Shared collection.** `GET /catalog` and `GET /catalog/{garment_id}/image` use active records in `catalog_garments`, `catalog_images`, and private bucket `catalog-images`. Search/category choices are controls. Returned garment names, prices, metadata, and images are backend values.
- **`/catalog/[id]` — Shared garment details.** `GET /catalog/{garment_id}` and the authenticated image GET source category, name, brand, color, material, size, notes, and optional price from the same catalog storage. INR is the existing contract's display currency. Removed an unreachable preview notice. Local list read and catalog database tests passed.
- **`/outfits` — Saved outfits.** `GET /outfits` reads `saved_outfits` and `outfit_items`. Filters and cursor pages are requested from the server. Outfit names, occasion, description, and item counts use the returned records. Only filters and page count remain in the shared in-memory drafts. On refresh failure the screen clears prior rows and exposes retry.
- **`/outfits/new` — Outfit builder.** `GET /wardrobe`, `GET /catalog`, and their detail/image GET routes populate the picker. `POST /outfits` writes `saved_outfits` and `outfit_items` with references to owned wardrobe garments or accessible catalog garments. Selected references are unsaved until the write succeeds.
- **`/outfits/[id]` — Outfit detail and editing.** `GET /outfits/{outfit_id}`, `PATCH /outfits/{outfit_id}`, `PUT /outfits/{outfit_id}/items`, and `DELETE /outfits/{outfit_id}` read and write the outfit and its associations. The editor sends only edited metadata. It no longer attempts to render an unsupported outfit image URL. In either outfit editor the selected garment label comes from its actual list row or authenticated detail GET, including when its source is off the active page. Missing details display an unavailable state. No numbered placeholder is used as a garment name.
- **`/recommendations` — Outfit suggestions.** `POST /recommendations` and `GET /recommendations` return deterministic server-generated results and reasons from `recommendation_requests` and `recommendation_results` using eligible wardrobe/catalog pieces. `POST /recommendations/{recommendation_id}/save` writes `saved_recommendations`. `POST /outfits` with the recommendation ID writes a real outfit and item associations. No frontend matching or fake scores. The UI displays results and reasons, and does not show the server score.
- **`/recommendations/saved` — Saved ideas.** `GET /recommendations/saved` returns `saved_recommendations` joined to eligible results and garments. `DELETE /recommendations/saved/{saved_id}` removes the bookmark. Unavailable source pieces show the server-indicated unavailable state. Fresh local login retrieved the saved record and a second user could neither save the first user's result nor remove the first user's bookmark.
- **`/try-on` — Prior jobs.** `GET /try-on/jobs` reads `tryon_jobs`; `GET /try-on/jobs/{job_id}/input` reads authorized bytes via `tryon_images` and private bucket `tryon-inputs`. `POST /try-on/jobs/{job_id}/cancel` uses the owner-scoped transition. Visible dates, status, and input availability originate in the job response. New submissions and output generation are unavailable in the UI. No fabricated job or output image. Local empty history passed; transitions and private input access were covered in backend/database tests.

### Administration

- **`/admin` — Admin workspace.** Static links behind the backend-derived role gate. The workspace itself shows no fabricated metrics or items.
- **`/admin/catalog` — Manage shared collection.** `GET /admin/catalog` and `GET /admin/catalog/{garment_id}/image` return active and inactive catalog records plus private bytes where allowed. The current local customer got `403` on the admin list. Administrator behavior was covered by backend/database tests.
- **`/admin/catalog/new` — Publish item.** Multipart `POST /admin/catalog` writes `catalog_garments` and `catalog_images` with private bytes. The form starts blank.
- **`/admin/catalog/[id]` — Edit/archive.** `GET /admin/catalog/{garment_id}`, authenticated image GET, multipart `PATCH /admin/catalog/{garment_id}`, and `DELETE /admin/catalog/{garment_id}` use the same data sources. The delete operation deactivates the item and preserves its record. Hosted admin mutation was outside scope.

## Shared frontend state and data controls

- `session.tsx` uses Supabase Auth and the subject-bound access response. Each protected request reads the current token and rejects responses if the account changed while they were in flight. Native session storage uses SecureStore. Browser access tokens live in memory; the OAuth PKCE verifier is separate and short-lived. A web reload requires sign-in again by design.
- `useResource` scopes reads by route, subject, and request revision; it aborts superseded requests. A transport, HTTP, or invalid response error leaves no data. Added basic response-envelope validation for resource reads and for dashboard, wardrobe/catalog, picker, outfit list, and try-on list. Recommendations and saved ideas already validate their specific response shapes. This is not a second complete schema validator for every backend model.
- `draftStore` and `useDraft` hold user-entered unsaved values, selection, filters, and transient state per account in memory, cleared when identity changes. Recommendation saved indicators update after a successful backend write and reconcile on history refresh. They are not a separate persistence layer.
- `Fields`, `schema`, and `validation` define labels, allowed choices, and form constraints. `PhotoField` shows the chosen file before save. `GarmentCard`, `WardrobeImage`, `TryOnJobCard`, and the presentation helpers format returned data or show unavailable/error states. They have no substitute product records or images.
- FastAPI validates the Supabase JWT and resolves account eligibility. Its Data API adapter forwards the verified user's token with a publishable key to Supabase's `api` schema. Migration policies enforce subject ownership and trusted administrator membership. The normal mobile data path has no service-role fallback.

## Verification

- Render `GET /healthz` returned HTTP 200 in 0.44 seconds. Unauthenticated requests to dashboard, wardrobe, catalog, outfits, recommendations, saved recommendations, profile, body profile, settings, try-on history, catalog access, and deletion status all returned 401.
- Read-only metadata on `drape-drop-dev` (`xpqhqhpqzkjaycraukrj`) showed 18 recorded migrations through `202611090010`, all 22 application tables with enabled and forced RLS, and private `wardrobe-images`, `catalog-images`, and `tryon-inputs` buckets. This run checked the flags and migration count, without a new comparison of every stored SQL statement.
- Earlier authenticated hosted evidence is recorded in [Hosted Android login verification](../archive/backend/hosted-android-login-verification.md). This run did not sign in to hosted accounts, recheck authenticated hosted CRUD, exercise hosted SMTP/OAuth, or write hosted data.

### Local application and automated checks

- Expo web at `http://localhost:8082`, FastAPI at `http://127.0.0.1:8003`, and loopback Supabase/Mailpit were used for live smoke checks. Two disposable local accounts were established using independent link and OTP proofs. Their credentials and generated records were kept outside tracked files.
- Live local API checks exercised profile, measurements and preferences updates; wardrobe creates, image retrieval and edit; outfit create, metadata edit and item replacement; deterministic generation and save; owner isolation; empty try-on history; role denial; and retrieval of the same persisted records through a new Auth session and HTTP client. Dashboard API counts matched the created records.
- Mobile tests passed 90 cases. TypeScript, Expo lint, and Android export passed. The export is a bundle, with no new signed APK and no installed-device result.
- Backend pytest passed 407 cases, with 318 database-dependent cases skipped in the ordinary run. The disposable PostgreSQL runner with `--registration` applied all 18 migrations and passed the 318 database tests separately (308 application/foundation and 10 registration/preview).
- Native force-close/restart, physical camera/picker behavior, and full authenticated hosted acceptance remain unverified. ML stays deferred.

No deployment, Git commit, or hosted data changes were made for this audit.
