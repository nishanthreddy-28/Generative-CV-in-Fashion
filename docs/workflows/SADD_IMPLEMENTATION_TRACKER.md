# Drape & Drop SADD implementation tracker

## Scope and evidence

The supplied Software Architecture Design Document (SADD) defines Workflows 1–10. The supplied master brief sets an audit and review gate before implementation. This tracker follows that gate and keeps ML, MediaPipe inference, and LLM/RAG work deferred. The referenced `docs/Software-Architecture-Design.md` is absent from the checkout, so the audit used the attached SADD. Repository evidence comes from `main` at `92edaca` and the existing working tree, which includes uncommitted direct-auth and other changes. The older milestone reports capture historical snapshots.

The active path is Expo Router → Supabase Auth for identity and sessions, and Expo → FastAPI → Supabase PostgREST RPC for application data. FastAPI verifies the bearer JWT with cached JWKS and forwards the same user's token through `UserDataAPI`. The exposed `api` schema provides RPC entry points backed by private application tables, constrained roles and RLS. Supabase Storage separately protects image objects. Account deletion and image retention have trusted worker code. Evidence includes the [Expo routes](../../mobile/src/app), [JWT verification](../../backend/app/security.py), [request dependencies](../../backend/app/dependencies.py), [user-scoped adapter](../../backend/app/data_api.py), [API route wiring](../../backend/app/main.py), [migrations](../../supabase/migrations), and [workers](../../backend/workers).

### 2. Profile and optional onboarding — implemented locally; database/hosted verification pending

- **In place.** Existing owner-scoped `GET/PATCH /profile` and `GET/PATCH /profile/body` remain. Email confirmation and first OAuth entry open the optional onboarding screen; returning OAuth users with a reviewed profile continue to the dashboard. The user may capture or upload one body photo, saved as a version in a private JPEG-only Storage bucket. A stable upload UUID makes an uncertain upload response retryable without a duplicate object. `GET /onboarding`, `POST /onboarding/body-photo/{upload_id}`, `GET /onboarding/body-photo/{image_id}`, `POST /onboarding/body-photo/{image_id}/review`, and `DELETE /onboarding/body-photo/{image_id}` are owner-scoped. Review writes the user-confirmed name, location, units and optional measurements to the existing profile tables atomically and associates the reviewed image version. A replacement retires the previous image for trusted cleanup. The dashboard remains accessible; no gate or completed-extraction claim exists.
- **In place in the database candidate.** The forward onboarding migration adds private version metadata, one current draft per user, ownership RLS, Storage object boundaries, API grants, image-reconciliation support and account-deletion coverage. It does not install anything on hosted Supabase.
- **Remaining.** Complete the disposable PostgreSQL regression run and mobile tests/build after this checkpoint. Verify real bucket/RLS behavior only after separate hosted migration approval. Decide image retention duration and what body photo is needed for MediaPipe. MediaPipe extraction and its original-versus-confirmed result review remain deferred. An existing-account migration/cohort decision remains unresolved. Do not enforce mandatory onboarding while the processing provider is absent.
- **Evidence.** [Onboarding screen](../../mobile/src/app/profile/onboarding.tsx), [API routes](../../backend/app/onboarding.py), [candidate migration](../../supabase/migrations/202611230002_onboarding_foundation.sql), [onboarding API tests](../../backend/tests/test_onboarding_api.py), [onboarding database tests](../../backend/tests/test_onboarding_database.py), [profile API](../../backend/app/foundation.py), [body profile API](../../backend/app/body_profile.py).

### 3. Recommendations and personalization — implemented locally; hosted rollout pending

- **In place.** The existing owner-scoped `POST/GET /recommendations` rules-v1 workflow remains, along with saved recommendation bookmarks. Structured style and colour tags, preferred occasions, INR catalog-piece price bounds, and fit persist through the new personalization API. Fit reuses `body_profiles.fit`; current garment data has no fit attribute, so fit is stored but not scored. Deterministic rules use saved style/colour tags and preferred occasions, filter catalog candidates by entered price bounds, and keep an internal snapshot of the applied preferences with each request. The recommendation request/history HTTP contracts remain unchanged. Users can submit or update a like/dislike with a constrained reason and optional note; one owner/result record is upserted safely and can be removed. The recommendations screen displays controls only after feedback state loads successfully.
- **Database candidate.** [Personalization migration](../../supabase/migrations/202611230003_recommendation_personalization.sql) extends the existing preference row, snapshots request-time settings, and adds owner-linked `recommendation_feedback` with forced RLS and a unique owner/result constraint. It has only been tested in the disposable local PostgreSQL runner and is not applied to hosted Supabase.
- **Remaining.** Hosted JWT/PostgREST/RLS acceptance, retention duration and feedback purge policy, and deployment are pending. Fit-aware scoring requires a fit attribute for garments and a reviewed compatibility rule. Provider-based recommendations and wardrobe-gap suggestions remain deferred; no ML output is simulated.
- **Evidence.** [Recommendation screen](../../mobile/src/features/RecommendationsScreen.tsx), [preference screen](../../mobile/src/app/personalization.tsx), [recommendation API](../../backend/app/recommendations.py), [personalization API](../../backend/app/personalization.py), [saved recommendations API](../../backend/app/saved_recommendations.py), [API design](../backend/api-design.md).

### 4. Wardrobe management — partial; duplicate-photo checkpoint implemented locally

- **In place.** Real wardrobe CRUD, search, cursor pagination, category filtering, camera/gallery input and authenticated image bytes. Each garment retains one cover photo; the local gallery candidate adds up to eight ordered-by-upload private views. Upload uses a private bucket with metadata and cleanup.
- **Duplicate-photo checkpoint.** Creation now uses an owner-scoped normalized-image hash check through `create_wardrobe_checked`. Matching current wardrobe photos return HTTP 409 before garment insertion, with an explicit “Keep another item” confirmation in the editor. The database serializes matching create requests per user using a transaction advisory lock. The warning is advisory, not visual similarity or proof that two garments are identical. Existing direct write RPC compatibility remains; the warning is not an authorization boundary. Uploaded images rejected by the warning use the existing abandonment/cleanup path. Candidate migration: `202611230004_wardrobe_duplicate_warning.sql`; hosted rollout remains pending.
- **Gallery candidate.** `202611230005_wardrobe_gallery.sql` adds same-owner garment/image associations, upload-order listing, one existing cover reference, bounded attachment and safe cover selection. The garment editor exposes additional photos and removal. Primary removal requires choosing another cover first. Existing replacement retires the old cover; garment deletion retires associated photos. The attach RPC can safely replay; HTTP upload itself is not yet idempotent after an uncertain response. Tests and hosted rollout must be evaluated separately.
- **Remaining frontend/backend/database.** Extend editable attributes, implement HTTP upload retry reconciliation, supported retailer link import with a review step, and extend duplicate handling to multiple-photo associations. A normalized-image hash warning is now implemented for garment creation. The classifier and visual similarity stay deferred.
- **Checkpoint verification.** 57 wardrobe API tests, 308 existing PostgreSQL regressions and 51 registration/direct-auth/onboarding/personalization/duplicate-photo database checks passed. Frontend tests (85), typecheck, lint and web review build passed. No browser interaction or hosted Storage acceptance was performed for this checkpoint. Multi-photo, product import and linked deletion remain incomplete.

Design the outfit item history and unavailable-reference representation jointly with Workflows 5 and 8 before changing the restriction.
- **Tests/dependencies.** Confirm supported retailer hosts, product image handling and access restrictions. Validate outbound URL targets and redirects, bound response size and time, and block private-network destinations. Test image replacement, duplicate confirmation, linked deletion, partial-upload cleanup and two-user isolation.

### 5. Outfit creation and management — partial; duplication implemented locally

3. **Build non-ML preferences, then resolve the shared wardrobe/outfit data boundary.** Land private media and typed garment attributes, then unavailable-item preservation, safe retailer import, outfit duplication and library favorites/collections. 4. **Extend account lifecycle and release operations.** Add deactivation, reactivation and private export once data coverage is clear. Include each new table and bucket in deletion/retention tests before enabling the feature. Validate hosted worker operation, CORS and APK build configuration separately from local CI.
5. **Add provider-dependent workflows after service contracts are available.** Use separate contracts for MediaPipe, garment classification, recommendations, compatibility, try-on and chatbot/RAG. Confirm timeouts, credentials, data minimization, retention, permitted processing and result validation before wiring real providers.
